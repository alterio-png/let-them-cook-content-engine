## Methodology and limits verified in source

- `scripts/benchmark_g3a1.py:129` retries **only** status 503, preserves the immutable operation, defaults to at most 16 physical attempts, and raises `AssertionError` on exhaustion. Each completed duplicate must return 201 and each quota race must return exactly ten 201 plus ten 429. **All-503 is failure**, not logical success or an acceptable no-progress profile.
- At most 1,600 duplicate physical attempts and 320 distinct physical attempts can be generated by their default cohorts. The default path cannot exceed 16 attempts per logical operation; do not confuse this maximum with the measured maximum of five. The fifteen sleeps sum to 3.125–3.395 s, depending on deterministic 0–18 ms staggering. Socket timeout is 20 s per attempt, not a strict end-to-end logical deadline; the benchmark has no separate total-operation wall-clock deadline. The server receive timer bounds header/body input, and is canceled before application/SQL processing.
- The separate contract helper `upload_tests/g3a1/test_http_replicas.py:35` retries to a roughly 20 s monotonic deadline with fixed 15 ms sleeps. It does **not** use the benchmark's sixteen-attempt budget or retain retry counts. Its deadline is checked after a call returns. This is a correctness helper, not physical-attempt or throughput evidence.
- `HTTPReplica` uses `multiprocessing` spawn, fresh work directories, distinct PIDs and a fresh HTTP connection per physical attempt. `serve_replica` repeatedly calls `handle_request()`, but inherited `ThreadingMixIn` dispatches each accepted handler to a thread. The server is concurrent; the loop does not serialize requests.
- Fixture HTTP capacity is 64 active handlers and configured listen backlog 64 per replica; upload authority capacity is four DB transactions per replica, including lease heartbeat transactions. The default same-key cohort routes 50 caller threads to each replica, so it does not intentionally exceed the HTTP handler cap. It stresses the per-authority upload semaphore and SQL serialization; successful semaphore admission opens a new psycopg connection, rather than borrowing a persistent connection pool.
- The two upload authorities therefore permit up to eight upload DB connections **for this LOCAL_CRYPTO cohort**, not four server-wide or eight deployment-wide connections. Historical render routes have another semaphore, four per replica. `PostgresSessionChecker` opens one fresh short DB connection for every verified request, with no explicit session-connection semaphore, before route-level upload/render admission. HTTP handler caps indirectly bound concurrent session checks. Startup checks, administration, GoTrue's own pool, monitoring, reconcilers and other workers are separate consumers.
- The default load uses HS256 synthetic cryptographic JWTs and a dictionary session callback. Each retry creates a new client token and passes through signature/session checks before upload admission. It does not measure official Auth session DB lookup load. Official local GoTrue integration proves session behavior in a separate small functional suite; it is not a mixed-service capacity measurement.
- A 503 is recorded as backpressure by `HTTPWorkload`, but status alone cannot distinguish immediate HTTP-cap rejection from upload semaphore exhaustion, a failed DB connection, a PostgreSQL server/transaction error or another retryable DB fault. The shared HTTP handler maps broad psycopg failures to `503 database_unavailable`, while the benchmark records only numeric status and discards even the sanitized response error category. The archive proves **205 recovered 503 responses**, not a measured decomposition by cause.
- The benchmark's two tenant cohorts run sequentially. There is no competing-tenant fairness cohort, sustained offered-rate sweep, real Auth + render + upload contention, client retry queue measurement, listen backlog measurement, DB connection high-water or lock-wait measurement. A semaphore gives a cap, not FIFO or tenant fairness.

Keep client concurrency distinct from render-worker concurrency; the upload benchmark performs no FFmpeg render.

1. **Serial 1, baseline first:** one outstanding logical HTTP operation across both replicas, alternate replicas, repeat 100 duplicate reservations, twenty distinct keys against ten slots, and publication/read/restart checks. In a no-fault idle local run, proposed acceptance is one physical attempt per operation, no unexpected 503, expected terminal statuses, exact immutable-grant/receipt/object/quota invariants and complete cleanup. Record first attempts and retries even when zero. A 503 at this profile is an investigation failure, not a valid baseline just because retry later succeeds.
2. **Concurrency 2 only after serial baseline passes:** two outstanding logical HTTP operations total, one per replica, same fixed data/quotas and a series of finite measured windows. Keep server/DB caps fixed. Proposed no-fault acceptance remains expected first-attempt statuses without 503, no retry exhaustion, invariants/cleanup and both tenants/replicas making progress. Report p50/p95/p99 and sample size against serial baseline; predeclare local regression tolerances after collecting independent baseline repetitions. Do not derive cloud latency thresholds from this CI burst.
3. **Separate, explicitly tagged overload/recovery profile:** raise only bounded client offered load and include alternating tenants with their own quota; do not redefine the baseline to normalize 100% 503 or raise DB caps until a retry storm disappears. Retain a maximum sixteen physical attempts and add one monotonic total logical deadline, a finite client retry queue, cohort deadline and drain check. The exact local thresholds and per-tenant minimum progress share must be agreed before that future run. Expected acceptance includes nonzero useful progress for each admitted tenant, no exhausted operations for the workload claimed supportable, bounded queues/waits, invariant preservation, no rising backlog at fixed steady load, and return to baseline after removal of excess load. A deliberately impossible load may be classified as rejected overload only with explicit zero-progress/exhaustion totals; it cannot PASS as logical-service success.

For sustained/mixed work, add a separate profile with official local Auth and inherited render routes while uploads/heartbeat/reconciliation continue. Begin render-worker concurrency one, then two after the one-worker baseline passes; this does not change HTTP client concurrency labels. A valid total connection budget must sum independently configured consumers, reserve migration/recovery headroom, and be observed in PostgreSQL under the actual mix. Conservative sum-of-component caps may be useful for planning but is not measured usage or a proved supportable deployment size.
